# Kubernetes configuration for the Python 3.13 production image

Kustomize manifests (`kubectl kustomize`, no Helm) for the one image that serves LMS, Studio, every Celery queue and the deploy
jobs. The image and its contract are described in [`docker/py313/app/README.md`](../../docker/py313/app/README.md) (written by the
image change; the path is the contract, check it exists before relying on a detail).

## Layout

| Path | What |
| --- | --- |
| `base/` | ServiceAccount (no API token), Deployments `lms` and `cms`, one worker Deployment per queue, ClusterIP Services and PodDisruptionBudgets for lms/cms, three suspended CronJobs. Image is the placeholder `edxapp`. No Secret, no Ingress. |
| `base/workers.yaml` | Generated by `generate_workers.py` (table = staging `WORKER_SET`); the test fails when it drifts. |
| `jobs/` | Separate kustomization (Jobs are immutable): `db-init` (schema and seeds). Needs the ConfigMap `py313-bringup-env`, provided by the overlay. |
| `overlays/orbstack-local/` | Namespace `py313-prod-local`, local arm64 image, 1 replica each, small resources, only the default queue of lms and cms, in-cluster backing services in `backing/`. |
| `overlays/orbstack-local/jobs/` | `db-init` for the local overlay; `bringup.env` holds its non-secret `BRINGUP_*` values. |
| `overlays/orbstack-local-all-workers/` | Opt-in: the local overlay with all eight worker queues running. |
| `overlays/prod-example/` | README only: what a production overlay has to set. |
| `traefik/` | Traefik v3 controller for the local Traefik mode (namespace `traefik`, RBAC, CRDs, TLSStore, LoadBalancer Service), plus `coredns-custom.yaml`. Section "Traefik mode (production-like)". |
| `overlays/orbstack-local-traefik/` | The local overlay with real host names, HTTPS, Ingresses, a `static` Deployment (nginx) and the local CA in every application pod. |
| `scripts/`, `Makefile` | Local OrbStack run: `up`, `status`, `smoke`, `down` and the secret/config/Elasticsearch helpers (section "Local OrbStack run"). |
| `test_manifests.py`, `scripts/test_scripts.py` | Static checks, no cluster needed. |

Render: `kubectl kustomize k8s/py313/overlays/orbstack-local` (also `.../orbstack-local/jobs`, `base`, `jobs`).
Test: `uv run --no-project --python 3.13 python -B -m unittest discover -s k8s/py313 -p 'test_manifests.py' -v`.
The manifests deploy nothing by themselves; `scripts/` and `Makefile` do it for the local OrbStack cluster only.

## Contract with the image

Image contract (`docker/py313/app/README.md`; staging copy `triboo-doc/docs/staging/py313-docker-images/README.md` section 0):

- Ports 8000 (lms) and 8010 (cms); entrypoint `tini -- edxapp-entrypoint`; container `args` are `lms`, `cms`,
  `worker <lms|cms> <celery args>`, `manage <lms|cms> <args>`; any other command runs as given.
- uid/gid 1000, read-only root filesystem. Writable `emptyDir` volumes: `/tmp`, `/edx/var/log/lms`, `/edx/var/log/cms`,
  `/edx/var/edxapp/media`, `/edx/var/edxapp/data`. Nothing is mounted over `/edx/var/edxapp` (static root). Media and data are
  per-pod scratch; production keeps media in object storage (`DEFAULT_FILE_STORAGE`).
- Configuration is only the Secret `edxapp-config`, mounted read-only at `CONFIG_ROOT=/edx/app/edxapp/py313-config` with
  `defaultMode` 0440 and `fsGroup` 1000. The entrypoint exits 78 when a file is missing and 64 on a wrong system name.
- Readiness is `GET /heartbeat` (MongoDB, MySQL, Elasticsearch) with a `Host` header from `ALLOWED_HOSTS` (base uses `localhost`,
  which `generate_aws_config.py` always adds); liveness is TCP only, so a database outage makes pods unready instead of
  restarting them; the startup probe allows 15 minutes for the first import.
- Workers use the staging command shape: `--loglevel=info --queues=Q --hostname=Q.%h --concurrency=1|--pool=solo --heartbeat-interval=120`,
  replicas 1 (one consumer per queue, as staging proves).

## Configuration (automated for the local run by `scripts/gen-local-config`)

1. Backing services up (`overlays/orbstack-local/backing`), then `db-init`.
2. `generate_aws_config.py` needs root, `BRINGUP_*` variables (`jobs/bringup.env` plus the Secret values, `BRINGUP_ES_USE_SSL=true`,
   `BRINGUP_ES_CA_CERTS`, `BRINGUP_ES_USER`, `BRINGUP_ES_PASSWORD`, `BRINGUP_STATE_DIR=/edx/var/edxapp`, `BRINGUP_SERVICE_GROUP`,
   `/startup/jwt-private.pem`) and writes four files into a scratch directory. It cannot be a manifest here: it must run as uid 0,
   which the hardening test forbids, and its output is the Secret. Turn the files into `edxapp-config` without printing them.
3. Set `LOG_DESTINATION` to `console` in both env files before creating the Secret.

The `JWT_PRIVATE_SIGNING_KEY` of the LMS is written into `lms.auth.json` from `/startup/jwt-private.pem`, so no separate key file or
Secret key exists; the local scripts generate that RSA key with `openssl genrsa` (as staging does) and mount it only into the throwaway container.

### Elasticsearch

The local Elasticsearch mirrors staging: security on, HTTPS only. The platform checks the certificate in Python 3.13 strict mode
and by host name, so the init container creates a CA and a node certificate for `elasticsearch`, `elasticsearch.<ns>.svc[.cluster.local]`
and `localhost` (`elasticsearch-certutil`; the generated CA has `keyUsage keyCertSign`; the same commands were verified with a
Python 3.13 handshake against a throwaway container). After the pod is running:

- Public CA for the Secret: `kubectl -n py313-prod-local exec elasticsearch-0 -- cat /usr/share/elasticsearch/config/certs/ca/ca.crt` (key `es-ca.crt`).
- Application role and user, as `03a-elasticsearch.sh`: role `py313_search` with cluster `monitor` and index privileges `all` on
  `<BRINGUP_ES_INDEX_PREFIX>_*` (`ELASTIC_SEARCH_INDEX_PREFIX` is the prefix plus `_`), user with that role; run the `PUT _security/role/...` and
  `_security/user/...` calls with `curl --cacert` inside the pod, authenticating with `$ELASTIC_PASSWORD` (already in its environment),
  and pass the new password on stdin, not argv.

## Termination grace period of workers (OWNER DECISION, open question Q8)

Staging stops workers with `stopwaitsecs=432000` (5 days). Kubernetes cannot practically wait that long, so the base ships
`terminationGracePeriodSeconds: 3600` on every worker as a placeholder. Celery treats SIGTERM as a warm shutdown, so a task
longer than the grace period is killed and must be retried (check `acks_late` and task idempotency before choosing). Override per
environment (the local overlay does it with 60):

```yaml
patches:
  - target:
      kind: Deployment
      labelSelector: app.kubernetes.io/component=worker
    patch: |-
      apiVersion: apps/v1
      kind: Deployment
      metadata:
        name: any
      spec:
        template:
          spec:
            terminationGracePeriodSeconds: 14400
```

Web pods use 60 (gunicorn `--graceful-timeout` default 30 s plus a 5 s preStop sleep).

## Cron

`base/cronjobs.yaml` has `course-email-reminder` (`0 4 * * *`), `send-ilt-daily-mail` (`0 5 * * *`), `metrics` (`0 3 * * *`), all
`suspend: true`. The Platform `scripts/*.sh` call `sudo` and a host-only env file, so the jobs run the same Python through
`edxapp-entrypoint manage lms ...`. Enable one with a patch `spec.suspend: false`. No `timeZone` is set: schedules use the
controller-manager time zone; staging's `cron.d` used the host time zone (unknown).

```bash
kubectl -n py313-prod-local port-forward svc/cms 18010:8010
```

## Local OrbStack run

Everything below is for the OrbStack Kubernetes cluster only. Every script refuses to run unless `kubectl config current-context` is
`orbstack` (override on purpose with `ALLOW_CONTEXT=<name>`), passes `--context` to each kubectl call, and works in the namespace
`py313-prod-local` only (fixed in `scripts/lib.sh`; `down` also checks the namespace label). No script removes Docker containers, images or volumes.

Prerequisites: OrbStack with Kubernetes enabled (StorageClass `local-path`), `kubectl`, `docker`, `openssl`, `uv`; the images
`edxapp:py313-prodimage-3c3f2f7-local` (image change; the tag is read from `overlays/orbstack-local/kustomization.yaml`),
`mysql:8.4.13`, `mongo:8.0`, `elasticsearch:8.19.0`, `rabbitmq:4.3`, `memcached:1.6.45` in the local Docker daemon (nothing is pulled);
about 4 GiB of free memory in the Docker VM for the default overlay, about 6 GiB with all workers.

```bash
make -C k8s/py313 k8s-local-test      # manifests and script tests, no cluster
make -C k8s/py313 k8s-local-up        # ~1 min with warm images; APP_OVERLAY=overlays/orbstack-local-all-workers for all queues
make -C k8s/py313 k8s-local-smoke     # port-forwards 18000/18010, heartbeats, pages, one Celery task
make -C k8s/py313 k8s-local-admin     # one administrator (password typed without echo); the LMS signs in by e-mail, the database has no users until then
make -C k8s/py313 k8s-local-status
make -C k8s/py313 k8s-local-down      # deletes the namespace (and its PVCs); .local/ stays unless PURGE_LOCAL=1
```

What `up` does (each step is also a script and can be rerun): namespace -> `gen-local-secrets` (random credentials into git-ignored
`.local/`, mode 700/600, and the Secret `backing-credentials`; existing files are kept so a rerun never rotates a password that a database
volume was initialised with) -> backing services -> `setup-elasticsearch` (copies the CA to `.local/es-ca.crt`, creates role and user
`py313_search` with `kubectl exec`; passwords go in through stdin and `curl --config`, never argv) -> `gen-local-config` (runs the
image's `/startup/generate_aws_config.py` as uid 0 in a throwaway `docker run --rm --network none`, sets `LOG_DESTINATION=console`,
verifies the result with `scripts/postprocess_config.py`, creates the Secret `edxapp-config`) -> `db-init` Job -> application overlay -> rollouts.
Secrets reach the cluster through `kubectl create secret ... --dry-run=client -o yaml | kubectl apply --server-side` (no YAML with values on
disk; server-side apply keeps the data out of the `last-applied-configuration` annotation).

Decisions taken here (the former open questions):

- **Database name** (was Q3): `py313_startup_local`, so the Platform `database_guard.py` accepts it without `BRINGUP_ADOPTED_DATABASE`.
  The database is new; no wipe exists. `up` skips a completed `db-init` (`FORCE_DB_INIT=1` reruns it). The Job has `ttlSecondsAfterFinished: 86400`, so completion is recorded durably
  as the namespace annotation `py313.learningtribes.com/db-init-completed=<database name>` (set after the Job succeeded; a still-complete Job of an older run is backfilled).
- **`LOG_DESTINATION`** (was Q2): post-processed to `console` before the Secret is created; the application log appears in `kubectl logs`.
- **Site domains and scheme**: `localhost:18000` / `localhost:18010`, `BRINGUP_SCHEME=http` (so `SESSION_COOKIE_SECURE` is false); no cookie domain.
- **Static files** (Q4): not served in this flow (see open question 2); the Traefik mode serves them with nginx. **`metrics` cron** (Q5): stays suspended. **Resources** (Q6): measured, below.
- The pods log the Django `DisallowedHost` traceback for an unknown `Host` (that is the smoke test's negative check, not a fault).
- `kubectl apply` reports the StatefulSets and PodDisruptionBudgets as `configured` on every run without restarting any pod
  (client-side apply and defaulted fields); a changed StatefulSet template does restart its pod (a crash-looping pod must be deleted by hand).

Measured on this laptop (OrbStack Docker VM 15.66 GiB, 10 CPUs, arm64; `docker stats` and the cgroup `memory.peak`; no metrics-server,
so `kubectl top` is unavailable): one run, idle right after `up` and the smoke test, memory only. The web rows were re-measured after raising gunicorn to two workers (below); the other rows are from the earlier run.

The overlay's `resources` for lms, cms and workers are set from these numbers (about 2x the peak as limit; with two workers lms is 250m/768Mi to 2 CPU/2Gi and cms 100m/512Mi to 1 CPU/1536Mi). They describe one idle
instance with a handful of requests, not load. Start-up: lms and cms were Ready 10-11 s after the container started on a warm node;
`db-init` took 26 s on a populated database.

Web concurrency and probes (Studio and LMS): the legacy gunicorn configuration is `sync` workers with `timeout 300`, no threads (production 45 LMS / 16 Studio
workers, staging 2 / 1). With one sync worker the readiness probe on `/heartbeat` queues behind a long request (an import, an export, a slow page); after
the probe fails the pod leaves the Service and everybody gets 503. The base and the local overlay therefore run **two sync workers** and the readiness probes
tolerate six failures (`failureThreshold: 6`, 60 s) instead of three, so one slow request occupies one worker while the other answers the probe. No threads,
no other worker class and no `GUNICORN_CMD_ARGS`, because those would change application semantics (thread-safety of the legacy code); a test guards that.
Both workers busy for more than 60 s still takes the pod out of rotation, as it does in production when all workers of a host are busy; capacity beyond two workers is a replica or `GUNICORN_WORKERS` decision after a load test.

Studio course import and export: Studio writes the uploaded archive below `GITHUB_REPO_ROOT` and hands it to a Celery task (`import_olx`, queue `edx.cms.core.default`,
run by `worker-cms-default`) through `course_import_export_storage`, a `FileSystemStorage` under `MEDIA_ROOT` unless `COURSE_IMPORT_EXPORT_BUCKET` is set.
Two settings pointed at the read-only image path `/edx/app/edxapp/data` (`GITHUB_REPO_ROOT` defaults to it; the generated `MODULESTORE` carries `fs_root` for the XML/split
stores, and the split store creates directories there when a course loads), so `scripts/postprocess_config.py` (run by `gen-local-config`, checked by the same script)
sets both to the writable `data` volume (`/edx/var/edxapp/data`) and refuses a config that differs. Volumes of the cms and its workers: `/tmp` 3 Gi (the
2 GiB request body is spooled there), `media` 3 Gi, `data` 6 Gi (each upload stays in `data` until the pod restarts, which is Platform behaviour; 6 Gi holds two maximal imports).
Locally the cms and both cms workers share one PVC `studio-media` (6 Gi) as `media`, because the web pod stores the archive there and the worker reads it; the `local-path`
volume is `ReadWriteOnce` but all pods run on the one node. In a real cluster use S3 (`COURSE_IMPORT_EXPORT_BUCKET`) or a ReadWriteMany volume. `k8s-traefik-smoke` exports a course to a tarball in the cms pod (`export_course_to_tarfile`, which writes below `fs_root`), uploads it to Studio over HTTPS, and checks import status 4,
the worker log and the removal of the temporary directory; the HTTP export endpoint and its download are not exercised (`/media` is not served locally).

Smoke test (`scripts/smoke`): `/heartbeat` with `Host: localhost` and with the site host, LMS `/` and `/login`, Studio `/signin`, an unknown
`Host` (400), then one Celery task: `kubectl exec deploy/lms -- edxapp-entrypoint manage lms shell` calls
`openedx.core.djangoapps.heartbeat.tasks.sample_task.apply_async()` (returns `True`, no side effects), waits for the result over the
memcached result backend, and the script requires the same task id as `received` and `succeeded` in the log of `worker-lms-default`.
This proves broker routing to `edx.lms.core.default`, the worker's task registry and the result backend; it does not prove the other
queues (run with the all-workers overlay, `rabbitmqctl list_queues -p py313` shows one consumer on each) or any real task.

Known limitations: no styled pages and no ingress or TLS in the default flow (the Traefik mode serves both); media and data are per-pod scratch;
no mail relay (console backend); no Studio or LMS user exists (staging `12-admin.sh` has no counterpart yet); Elasticsearch runs without
read-only root (documented exception, `WRITABLE_ROOT_ALLOWED` in the test).

## Traefik mode (production-like)

The port-forward flow above stays the default. `INGRESS=traefik` runs the same stack behind Traefik with host names, HTTPS and static
files: LMS `https://lms.local-prod.7mud.com`, Studio `https://studio.local-prod.7mud.com` (`BASE_DOMAIN=local-prod.7mud.com`, a public
wildcard DNS record that resolves to `127.0.0.1`; there is no `preview.` host because the seed creates two Sites only).

```
browser --80/443--> OrbStack LoadBalancer --> Traefik (ns traefik, :8000/:8443)
                      web: 301 -> https      |  host lms.*     /        -> svc lms:8000
                      websecure: TLS (TLSStore |  host studio.*  /        -> svc cms:8010  (Middleware studio-body-limit)
                      default = local-prod-tls)|  both hosts     /static  -> svc static:8080 (nginx, files copied from the image)
pods --https://lms.*--> CoreDNS rewrite (coredns-custom) --> Traefik ClusterIP, trusting the local CA through SSL_CERT_FILE
```

Prerequisites: those of the local run, plus `openssl` 3, image `traefik:v3.7.19` and `nginxinc/nginx-unprivileged:1.31.7-alpine` in the local Docker
daemon, and free host ports 80 and 443 (OrbStack publishes the LoadBalancer there).

```bash
make -C k8s/py313 k8s-traefik-up        # = INGRESS=traefik scripts/up: a fresh namespace in Traefik mode (~2 min)
make -C k8s/py313 k8s-traefik-doctor    # read-only host diagnosis; prints the steps that only you can do
make -C k8s/py313 k8s-traefik-smoke     # curl --noproxy '*' --resolve --cacert <local CA>; creates and deletes a test user
make -C k8s/py313 k8s-traefik-status
make -C k8s/py313 k8s-traefik-down      # removes what the mode created; the namespace py313-prod-local stays
```

Switching mode changes the site domains stored in the database (`seed_local_host_sites.py` only creates Sites, it does not rename them),
so `up` records the mode as an annotation on the namespace and refuses to apply the other mode to an existing one. To switch:
`make k8s-local-down` (or `k8s-traefik-down` to keep the data and only drop the ingress), then `up` in the other mode. The default flow
without `INGRESS` is unchanged.

User-side steps (the scripts never edit Clash, `/etc/hosts` or the keychain, and never use sudo; `k8s-traefik-doctor` prints exact
commands and an undo for each):

1. Clash (mihomo) must resolve the domain with the real answer and route it `DIRECT`: rule `DOMAIN-SUFFIX,local-prod.7mud.com,DIRECT` and
   `dns.fake-ip-filter: '+.local-prod.7mud.com'`; the doctor detects fake-IP answers (198.18.0.0/15) and a proxy that does not reach Traefik.
2. Trust the local CA in the login keychain (`security add-trusted-cert ...`; Firefox has its own store). The CA carries name constraints: DNS, e-mail and URI names are
   limited to `local-prod.7mud.com`, and every IPv4 and IPv6 address is excluded (a name type without a constraint is unconstrained in X.509, and
   `excluded;email:.` is accepted by OpenSSL but does nothing, so e-mail and URI are bounded with `permitted`). A CA created by an older script lacks the IP/e-mail/URI parts;
   `gen-local-tls` keeps it (it is trusted in your keychain) and warns, and `k8s-traefik-doctor` reports it with the exact replacement steps.

`scripts/gen-local-tls` (run by `up`) writes `.local/tls/` (git-ignored; CA key mode 600; ECDSA P-256; CA 10 years; wildcard leaf 397 days
with SAN `*.local-prod.7mud.com` and `local-prod.7mud.com`). A rerun keeps both unless the leaf is expired, has a different SAN or no longer verifies.
It creates the Secret `local-prod-tls` (namespaces `traefik` and `py313-prod-local`) and the ConfigMap `local-ca-bundle` (the image's system
bundle plus the local CA, mounted at `/etc/local-ca` with `SSL_CERT_FILE` and `REQUESTS_CA_BUNDLE` in every application pod and job; the
Elasticsearch CA is separate and unaffected). `PURGE_LOCAL=1 scripts/down` keeps `.local/tls` unless `PURGE_TLS=1`.

Real certificates (ACME DNS-01 with the Aliyun `alidns` provider) are documented, not implemented: Traefik would get a `certificatesResolvers`
entry and the credentials from a git-ignored `.local/acme.env` that you fill (`ALICLOUD_ACCESS_KEY`, `ALICLOUD_SECRET_KEY`); nothing reads it today.

What the application sees: `BRINGUP_SCHEME=https` (`SESSION_COOKIE_SECURE`, `X-Forwarded-Proto` trusted through `SECURE_PROXY_SSL_HEADER`),
`BRINGUP_SESSION_COOKIE_DOMAIN=.local-prod.7mud.com` (one login for both hosts), site domains and `ALLOWED_HOSTS` equal to the two hosts.
Static files: the `static` pod copies `/edx/var/edxapp/staticfiles` from the application image into an `emptyDir` (initContainer) and nginx
serves it at `/static/` (LMS) and `/static/studio/` (Studio), with the production nginx rules: `.json`/`.xml` at the top level and
`README.TXT` are 403, content-hashed files are `public, max-age=31536000, immutable`, others `max-age=300`, GET/HEAD only. `/media` is
not served (per-pod scratch). The app emits HSTS (2 years, `includeSubDomains`) for these names.

Traefik settings worth knowing: no `forwardedHeaders.trustedIPs`, so Traefik rewrites `X-Forwarded-*` itself; `--global.aliasHeadersStrategy=delete`;
the redirect target is `:443` (a named entry point would put the container port 8443 in `Location`); `respondingTimeouts` read 0 s / write 300 s /
idle 180 s; encoded `/ \ % ? # ;` are allowed and NUL is refused (explicitly, v3 changed the defaults); `safeNaming=false` keeps the `<ns>-<name>@kubernetescrd`
form that the Studio Ingress annotation needs; both providers watch `py313-prod-local` and `traefik` only. The Studio body limit
(`maxRequestBodyBytes` 2147483648, the production nginx `client_max_body_size 2048M`; the buffering spool is a 3 Gi `/tmp` emptyDir) is attached
to the Studio Ingress only, so static files are unaffected. The Traefik CRD provider needs all ten `traefik.io` CRDs and read access to all of them
(with fewer, it logs reflector errors and Studio answered 404); `traefik/crds/crds.yaml` is the verbatim upstream v3.7.19 file (sha256 in its header).

Blast radius (everything outside `py313-prod-local`, all labelled `py313.learningtribes.com/feature=traefik-local`):
Namespace `traefik`; the ten Traefik CRDs; ClusterRole and ClusterRoleBinding `traefik-py313-local` (only `ingressclasses` and `nodes`, read-only: Traefik starts a Node informer and does not sync without it) plus a Role and RoleBinding of the same name in `traefik` and in `py313-prod-local` (services, secrets, configmaps, endpointslices, ingresses, `ingresses/status`, the ten `traefik.io` kinds; Traefik cannot read a Secret of another namespace). The `py313-prod-local` Role is installed by `traefik-install` (`traefik/app-rbac/`) and removed by `traefik-down`; it disappears with the namespace on `k8s-local-down`; ConfigMap `kube-system/coredns-custom`
(key `local-prod.override`) and a CoreDNS rollout restart; host ports 80 and 443. The `coredns` ConfigMap itself is never modified.
Rollback: `make k8s-traefik-down` deletes exactly those (it refuses a CRD, ConfigMap key or namespace that is not labelled or has foreign content),
restarts CoreDNS and keeps `py313-prod-local`, `local-prod-tls` and `local-ca-bundle` for a later `up`; `k8s-local-down` removes the namespace.

Verified on this laptop (arm64, OrbStack, Traefik v3.7.19, 2026-11-18, `make k8s-traefik-smoke`):

- `/heartbeat` over HTTPS for both hosts: 200 with the local CA; port 80 answers 301 with `Location: https://<host>/<path>`; unknown Host: 404.
- LMS `/login` and Studio `/signin`: 200 `text/html`; a hashed CSS (`text/css`) and JS (`application/javascript`) from `/static/` and `/static/studio/`: 200, immutable cache header;
  `staticfiles.json` 403; path traversal 404.
- Login: `POST /login_ajax` (LMS) and `/login_post` (Studio) with a run-time random password (never printed) return `success: true`; `sessionid`,
  `edxloggedin`, `edx-user-info` carry `Secure` and `Domain=.local-prod.7mud.com`; the LMS session opens Studio `/home/` and the Studio
  session opens LMS `/dashboard` (200). An `Origin: http://` login is refused (403, so the app sees scheme https); a client-sent
  `X-Forwarded-Proto: http` is overwritten (the underscore spelling is also harmless, but gunicorn drops it itself, so that check does not prove the Traefik option).
- In-cluster (lms and cms pods): both names resolve to the Traefik ClusterIP; `requests` and `urllib` reach `https://lms.local-prod.7mud.com/heartbeat`
  with the mounted bundle; the system bundle alone rejects it (negative control).
- Body limit: with the Middleware lowered to 1024 bytes a 4 KiB POST to Studio is 413, the same POST to LMS is not (403 from the app); restored afterwards.
- Celery smoke still passes; the port-forward flow (`k8s-local-up`/`-smoke` on ports 28000/28010) passed before this mode was added (the namespace is in Traefik mode now, so only the server-side dry run of both port-forward overlays was repeated). `k8s-local-test`: 57 manifest and 34 script tests, plus 27 image tests.
- Studio course export (management command) and import over HTTPS through the cms and its worker (status 4, worker log "Course import successful"/"Temp data cleared"); Traefik logs no `forbidden` after a restart with the namespaced RBAC.
- Memory (idle after the smoke): Traefik 35 MiB, static (nginx) 8 MiB, CoreDNS 15 MiB; whole namespace plus controller about 3.0 GiB. `kubectl top` is unavailable.

Differences from production: a local CA instead of real certificates; the OrbStack LoadBalancer instead of a cloud load balancer or hostPort; one replica
each; no WAF, rate limit or access-log shipping; the static files are copied from the image instead of served from the CDN or an nginx on the host;
no security headers beyond what the app sets (production nginx adds none either); Ingress objects only, no IngressRoute.

Not proven: behaviour in a real browser behind Clash and AnyConnect (the doctor proves the system proxy path with curl only), real certificates and ACME,
parity with the production Traefik configuration, `preview.` hosts, media uploads, and a Studio import of a large course against the 2 GiB limit (only a small course was imported). Production needs S3 or a ReadWriteMany volume for the import hand-off.

## Open owner decisions and questions

1. **Q8**: worker `terminationGracePeriodSeconds` (above); 3600 is not an agreed value.
2. **Static files** are not served by gunicorn (`DEBUG` only, no WhiteNoise in the settings). Browser flows need nginx or a sidecar
   serving `/edx/var/edxapp/staticfiles` (image README: sidecar, nginx `FROM` the image, or object storage). Not in the base; the Traefik overlay implements the sidecar-less variant (a `static` Deployment).
   Verified locally for the base: the CSS referenced by `/login` exists in the image and gunicorn answers 404 for it. Pages return 200 but render unstyled.
3. **Web resources** of the base (lms 1 Gi request / 3 Gi limit with 2 gunicorn workers, cms 768 Mi / 2 Gi, workers 512 Mi / 1.5 Gi, 1 Gi / 3 Gi
   for `high_mem`) are still estimates from staging figures (1.52 GiB PSS for five workers); production hosts run 45 / 16 workers. Only the
   local overlay carries measured values (section "Local OrbStack run").
4. **Worker liveness**: workers have no probe. A hung worker is not detected (`celery inspect ping` with the custom hostname is possible but heavy).
5. **`metrics` cron** (left suspended in every overlay, not exercised locally) reads `/edx/var/log/lms/metrics_*.csv.<yesterday>` written by the LMS pods (a per-pod `emptyDir` here) and writes
   `/edx-data/metrics`; without shared storage or a changed log target it cannot match staging. Also needs the `api_user` account.
6. **`db-init` rerun safety**: proven once on the local database (a second Job on the populated database completed: `get_or_create`
   seeds reported `created: False`, 0 deferred constraints reconciled); not proven after a *partial* failure or on a production-sized database. No wipe is provided on purpose
   (staging `07` drops every table and Mongo collection after a backup and an explicit confirmation).
7. **Cron time zone** (above) and the `activeDeadlineSeconds` of the cron jobs (2 h, metrics 4 h) are placeholders.
8. **Secret management** for a real environment (external secrets, sealed secrets) is outside this change.
9. **Production Traefik parity** (Traefik mode): which entry points and ports, which middlewares (security headers, rate limit, buffering, compression, the
   Studio body limit), `Ingress` or `IngressRoute`, the certificate resolver, whether `forwardedHeaders.trustedIPs` must trust an upstream load balancer
   (here Traefik is the edge and trusts nobody), and the ACME provider and credential storage. The local mode assumes the answers given in its section.
