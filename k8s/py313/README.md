# Kubernetes configuration for the Python 3.13 production image

Kustomize manifests (`kubectl kustomize`, no Helm) for the one image that serves LMS, Studio, every Celery queue and the deploy
jobs. The image and its contract are described in [`docker/py313/app/README.md`](../../docker/py313/app/README.md) (written by the
image change; the path is the contract, check it exists before relying on a detail).

## Layout

| Path | What |
| --- | --- |
| `base/` | ServiceAccount (no API token), Deployments `lms` and `cms`, one worker Deployment per queue, ClusterIP Services and PodDisruptionBudgets for lms/cms, three suspended CronJobs. Image is the placeholder `edxapp`. No Secret, no Ingress. |
| `base/workers.yaml` | Generated by `generate_workers.py` (table = staging `WORKER_SET`); the test fails when it drifts. |
| `jobs/` | Separate kustomization (Jobs are immutable): `db-init` (schema and seeds). Needs the ConfigMap `py313-bringup-env`, provided by the overlay. |
| `overlays/orbstack-local/` | Namespace `py313-prod-local`, local arm64 image, 1 replica each, small resources, only the default queue of lms and cms, in-cluster backing services in `backing/`. |
| `overlays/orbstack-local/jobs/` | `db-init` for the local overlay; `bringup.env` holds its non-secret `BRINGUP_*` values. |
| `overlays/orbstack-local-all-workers/` | Opt-in: the local overlay with all eight worker queues running. |
| `overlays/prod-example/` | README only: what a production overlay has to set. |
| `test_manifests.py` | Static checks, no cluster needed. |

Render: `kubectl kustomize k8s/py313/overlays/orbstack-local` (also `.../orbstack-local/jobs`, `base`, `jobs`).
Test: `uv run --no-project --python 3.13 python -B -m unittest discover -s k8s/py313 -p 'test_manifests.py' -v`.
Nothing here deploys anything; deploy scripts and a Makefile are a separate change.

## Contract with the image

Image contract (`docker/py313/app/README.md`; staging copy `triboo-doc/docs/staging/py313-docker-images/README.md` section 0):

- Ports 8000 (lms) and 8010 (cms); entrypoint `tini -- edxapp-entrypoint`; container `args` are `lms`, `cms`,
  `worker <lms|cms> <celery args>`, `manage <lms|cms> <args>`; any other command runs as given.
- uid/gid 1000, read-only root filesystem. Writable `emptyDir` volumes: `/tmp`, `/edx/var/log/lms`, `/edx/var/log/cms`,
  `/edx/var/edxapp/media`, `/edx/var/edxapp/data`. Nothing is mounted over `/edx/var/edxapp` (static root). Media and data are
  per-pod scratch; production keeps media in object storage (`DEFAULT_FILE_STORAGE`).
- Configuration is only the Secret `edxapp-config`, mounted read-only at `CONFIG_ROOT=/edx/app/edxapp/py313-config` with
  `defaultMode` 0440 and `fsGroup` 1000. The entrypoint exits 78 when a file is missing and 64 on a wrong system name.
- Readiness is `GET /heartbeat` (MongoDB, MySQL, Elasticsearch) with a `Host` header from `ALLOWED_HOSTS` (base uses `localhost`,
  which `generate_aws_config.py` always adds); liveness is TCP only, so a database outage makes pods unready instead of
  restarting them; the startup probe allows 15 minutes for the first import.
- Workers use the staging command shape: `--loglevel=info --queues=Q --hostname=Q.%h --concurrency=1|--pool=solo --heartbeat-interval=120`,
  replicas 1 (one consumer per queue, as staging proves).

## Secrets (never committed; created at run time)

`edxapp-config` (keys are file names, mounted as files):

| Key | Content |
| --- | --- |
| `lms.env.json`, `lms.auth.json`, `cms.env.json`, `cms.auth.json` | Output of `/startup/generate_aws_config.py`, with `LOG_DESTINATION` changed from `file` to `console` (the generator writes `file`). |
| `es-ca.crt` | Public CA of Elasticsearch when it is served over TLS; `BRINGUP_ES_CA_CERTS` must be `/edx/app/edxapp/py313-config/es-ca.crt`. |

`backing-credentials` (keys only):

| Key | Used by |
| --- | --- |
| `mysql-root-password`, `mysql-database`, `mysql-user`, `mysql-password` | MySQL pod, `db-init`. The database name must start with `py313_startup_` or `py313_rebuild_` (Platform `database_guard.py`) unless `BRINGUP_ADOPTED_DATABASE` names it. |
| `mongo-user`, `mongo-password` | MongoDB root user (authSource `admin`), `db-init`. |
| `rabbitmq-user`, `rabbitmq-password` | RabbitMQ default user (vhost `py313`), `db-init`. |
| `elastic-password` | Bootstrap password of the Elasticsearch `elastic` user. |
| `bringup-secret-key`, `bringup-xqueue-password` | Required by the `startup_*` settings of `db-init`; the same `bringup-secret-key` must be used when running `generate_aws_config.py`, which copies it into `SECRET_KEY`. |

The application's own Elasticsearch user and its password live in `lms|cms.env.json` (`ELASTIC_SEARCH_CONFIG`), not here.

## Configuration (run-time sequence for part C, not automated here)

1. Backing services up (`overlays/orbstack-local/backing`), then `db-init`.
2. `generate_aws_config.py` needs root, `BRINGUP_*` variables (`jobs/bringup.env` plus the Secret values, `BRINGUP_ES_USE_SSL=true`,
   `BRINGUP_ES_CA_CERTS`, `BRINGUP_ES_USER`, `BRINGUP_ES_PASSWORD`, `BRINGUP_STATE_DIR=/edx/var/edxapp`, `BRINGUP_SERVICE_GROUP`,
   `/startup/jwt-private.pem`) and writes four files into a scratch directory. It cannot be a manifest here: it must run as uid 0,
   which the hardening test forbids, and its output is the Secret. Turn the files into `edxapp-config` without printing them.
3. Set `LOG_DESTINATION` to `console` in both env files before creating the Secret.

### Elasticsearch

The local Elasticsearch mirrors staging: security on, HTTPS only. The platform checks the certificate in Python 3.13 strict mode
and by host name, so the init container creates a CA and a node certificate for `elasticsearch`, `elasticsearch.<ns>.svc[.cluster.local]`
and `localhost` (`elasticsearch-certutil`; the generated CA has `keyUsage keyCertSign`; the same commands were verified with a
Python 3.13 handshake against a throwaway container). After the pod is running:

- Public CA for the Secret: `kubectl -n py313-prod-local exec elasticsearch-0 -- cat /usr/share/elasticsearch/config/certs/ca/ca.crt` (key `es-ca.crt`).
- Application role and user, as `03a-elasticsearch.sh`: role `py313_search` with cluster `monitor` and index privileges `all` on
  `<BRINGUP_ES_INDEX_PREFIX>_*` (`ELASTIC_SEARCH_INDEX_PREFIX` is the prefix plus `_`), user with that role; run the `PUT _security/role/...` and
  `_security/user/...` calls with `curl --cacert` inside the pod, authenticating with `$ELASTIC_PASSWORD` (already in its environment),
  and pass the new password on stdin, not argv.

## Termination grace period of workers (OWNER DECISION, open question Q8)

Staging stops workers with `stopwaitsecs=432000` (5 days). Kubernetes cannot practically wait that long, so the base ships
`terminationGracePeriodSeconds: 3600` on every worker as a placeholder. Celery treats SIGTERM as a warm shutdown, so a task
longer than the grace period is killed and must be retried (check `acks_late` and task idempotency before choosing). Override per
environment (the local overlay does it with 60):

```yaml
patches:
  - target:
      kind: Deployment
      labelSelector: app.kubernetes.io/component=worker
    patch: |-
      apiVersion: apps/v1
      kind: Deployment
      metadata:
        name: any
      spec:
        template:
          spec:
            terminationGracePeriodSeconds: 14400
```

Web pods use 60 (gunicorn `--graceful-timeout` default 30 s plus a 5 s preStop sleep).

## Cron

`base/cronjobs.yaml` has `course-email-reminder` (`0 4 * * *`), `send-ilt-daily-mail` (`0 5 * * *`), `metrics` (`0 3 * * *`), all
`suspend: true`. The Platform `scripts/*.sh` call `sudo` and a host-only env file, so the jobs run the same Python through
`edxapp-entrypoint manage lms ...`. Enable one with a patch `spec.suspend: false`. No `timeZone` is set: schedules use the
controller-manager time zone; staging's `cron.d` used the host time zone (unknown).

## Local access

The base has no Ingress and OrbStack has no ingress controller:

```bash
kubectl -n py313-prod-local port-forward svc/lms 18000:8000
kubectl -n py313-prod-local port-forward svc/cms 18010:8010
```

`bringup.env` uses `localhost:18000` and `localhost:18010` as site domains for that reason.

## Open owner decisions and questions

1. **Q8**: worker `terminationGracePeriodSeconds` (above); 3600 is not an agreed value.
2. **Static files** are not served by gunicorn (`DEBUG` only, no WhiteNoise in the settings). Browser flows need nginx or a sidecar
   serving `/edx/var/edxapp/staticfiles` (image README: sidecar, nginx `FROM` the image, or object storage). Not in these manifests.
3. **Web resources** (lms 1 Gi request / 3 Gi limit with 2 gunicorn workers, cms 768 Mi / 2 Gi, workers 512 Mi / 1.5 Gi, 1 Gi / 3 Gi
   for `high_mem`) are estimates from staging figures (1.52 GiB PSS for five workers), not measurements; production hosts run 45 / 16 workers.
4. **Worker liveness**: workers have no probe. A hung worker is not detected (`celery inspect ping` with the custom hostname is possible but heavy).
5. **`metrics` cron** reads `/edx/var/log/lms/metrics_*.csv.<yesterday>` written by the LMS pods (a per-pod `emptyDir` here) and writes
   `/edx-data/metrics`; without shared storage or a changed log target it cannot match staging. Also needs the `api_user` account.
6. **`db-init` rerun safety** is derived from reading the scripts, not proven on a populated database; no wipe is provided on purpose
   (staging `07` drops every table and Mongo collection after a backup and an explicit confirmation).
7. **Cron time zone** (above) and the `activeDeadlineSeconds` of the cron jobs (2 h, metrics 4 h) are placeholders.
8. **Secret management** for a real environment (external secrets, sealed secrets) is outside this change.
